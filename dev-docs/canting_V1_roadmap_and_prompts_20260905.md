## 0. 使用方式

不要一次把本文所有 Prompt 发给开发 Agent。一次只执行一个阶段：开发团队交付报告 → 产品经理验收 → 再发送下一阶段 Prompt。

当前排期按“个人开发者 + AI 开发团队”估算：约 8–13 个实际开发日，加 7 天封闭测试。所有时间是区间，不是承诺；真实菜库质量和小米真机兼容性是关键路径。

## 1. 已核实的当前状态

- 主仓库：`D:\dev\canting`，Flutter，Android 优先。
- Git：`main` 比 `origin/main` 领先 3 个提交；当前有大量未提交的数据层、指南层、推荐引擎和测试改动。
- 当前静态检查：`dart analyze` 零问题。
- 当前完整测试：`flutter test --no-pub`，340/340 通过。
- 已实现：本地持久化、手动添加、分享图片/拍照/相册 OCR、菜品匹配、推荐引擎、7 天滚动台账、Android Widget 的代码与 Manifest 注册。
- 当前内置菜库：1004 道，约 640KB；其中绝大多数是估算数据，不能当作最终真实菜库。
- 当前匹配器支持 exact / contains / fuzzy / keyword / unmatched；`confidence >= 0.5` 会自动添加，关键词回退恰好为 0.5，存在“低信息量结果被直接接受”的产品风险。
- 当前 `user_custom_dishes` 能保存自定义菜品，但还没有完整表达品牌、糖型、杯型、做法、酱料、来源、确认状态和规则版本。
- 当前推荐引擎已有 `recommendable` 和部分质量标签过滤、7 天滚动调节；尚未形成完整的 28 天趋势层和“高风险食品每周暴露提醒”产品闭环。
- `canting_v0.1.0-beta.apk` 为 88,805,734 bytes；当前 debug APK 约 215MB。必须构建分析后再优化，不能直接归因于 Dart 代码或菜库。
- Android Widget 已注册，但尚未在用户的小米真机上完成发现、添加、刷新、重启后的完整验收。
- Nutradata 爬虫位于 `D:\dev\nutridata_crawl`。截至 2026-09-05 01:36 左右输出 2006/25668 条，成功日志未见失败；爬虫结束只是获得原始材料，不代表可以直接打包进 App。

## 2. 版本目标与范围

### V1 成功定义

1. 用户可在 Android 真机上完成“分享/选图 → OCR → 确认或纠正 → 保存 → 首页/历史/推荐更新”的闭环。
2. 未识别或低置信度商品不会静默记零，也不会被当成健康食品主动推荐。
3. 用户纠正过的商品在本机可复用，重复确认次数随使用下降。
4. 推荐规则确定、可解释、不可被用户数据改写；已知不健康和信息不足的高风险食品不主动推荐。
5. App 展示 7 天行动建议与 28 天趋势，不声称精确热量或医疗效果。
6. 小米真机核心流程、Widget 和发布包通过验收。

### V1 不做

- AI 在线识别、联网查询、社区、跨用户学习、后台外卖监控、订单通知识别、iOS 发布。

## P1：Nutradata 原料验收与紧凑菜库管线

### 开始条件

- 爬虫进程已经正常结束，输出文件不再增长。
- P0 已确认仓库没有其他会话写入。

### 给开发团队的 Prompt

```markdown
你现在负责餐盘 V1 的“Nutradata 原料验收与紧凑菜库管线”。

先完整阅读 `AGENTS.md` 和 `dev-docs/v1-baseline-audit_20260905.md`。

## 目标

把 `D:\dev\nutridata_crawl\output\dishes.jsonl` 当作只读原始材料，建立可重复、可审计的蒸馏管线；不要把原始页面数据直接复制进 App。

最终 App 只保留支持粗粒度语义归类、份量区间和安全推荐所必需的紧凑字段，不追求精确卡路里展示。

## 任务

1. 对原始 JSONL 做只读验收：
   - 总行数、唯一 ID、唯一名称、重复率、空字段率、解析失败率。
   - 配料、做法、单位量、宏量营养素字段的覆盖率。
   - 异常克重、异常单位、HTML残留、编码问题和明显抓取错误。
   - 随机抽样与高频外卖菜人工样本。
2. 单独输出数据许可风险说明：
   - 明确“能访问”不等于“允许再分发”。
   - 在许可未确认前，原始内容只能留在仓库外，不得提交或打包。
   - 对每个最终字段说明它是原文、计算值、标签还是估算值。
3. 设计分层管线：
   - raw：原始 JSONL，仓库外、只读。
   - normalized：名称、配料、做法、单位统一。
   - distilled：App 自有 schema，只保留类别贡献、份量档位、风险标签、别名候选、来源和置信度。
   - curated：人工审核的高频外卖核心集。
4. 不能简单把菜名列表全部作为推荐池。推荐候选必须满足数据完整度和安全政策。
5. 设计并实现确定性去重：同名、标点差异、地区后缀、做法变体不能产生随机覆盖。
6. 为蒸馏输出增加至少：
   - source_type
   - source_id
   - estimated
   - confidence
   - review_status
   - schema_version
7. 输出体积预算：比较 1004 道旧库与新库的 JSON 大小、压缩后大小、SQLite 初次导入耗时和冷启动影响。
8. 更新自动化测试：schema、重复、全零、非法枚举、风险标签冲突、迁移保留用户数据、同版本幂等。
9. 生成：
   - `dev-docs/nutridata-raw-acceptance.md`
   - `dev-docs/food-knowledge-distillation.md`
   - 机器可读统计 JSON

## 决策规则

- 原始字段缺失时必须标未知，不能用 0 伪装。
- 估算数据不能升级成“已验证”。
- 名称包含汉堡、三明治、烧烤不能单独决定健康结论。
- 酒精、含糖饮料、明确油炸/高盐/高糖可记账，但默认不能进入主动推荐池。

## 验收标准

- 同一输入重复运行得到字节级稳定或语义级稳定输出。
- 任何原始坏行都有计数和隔离文件，不会中止整个管线。
- 用户数据库迁移测试证明餐食记录和用户自定义画像不丢失。
- 静态检查和完整测试全绿。
- 未确认再分发许可时，不把 Nutradata 原始文本提交到仓库或 APK。

完成后提交管线报告、统计、体积对比和待产品确认项，不要继续做 UI。
```

## P2：本地商品语义画像与纠错飞轮

### 给开发团队的 Prompt

```markdown
你现在负责餐盘 V1 的“本地商品语义画像与用户纠错飞轮”。

先阅读 `AGENTS.md`、P1 数据报告、现有 `DishMatcher`、`MatchResult`、`user_custom_dishes`、OCR 记录页和数据库迁移测试。

## 用户故事

作为用户，当截图中出现“青青糯山”“香辣鸡腿堡”“小份巴斯克”等商品时，我希望 App 能归入奶茶/汉堡/甜品等结构类别；如果不能确定，我可以快速补充类别、糖型、杯型、份量或做法，并让 App 下次记住，而不是每次重复填写。

## 目标数据模型

在不破坏已有 `user_custom_dishes` 的前提下，评估扩展或新增 `UserFoodProfile`。至少表达：

- brandRaw / brandNormalized
- itemNameRaw / itemNameNormalized
- canonicalDishId（可空）
- semanticCategory
- preparation：fried / grilled / steamed / boiled / stir_fried / unknown
- sauceLevel：none / light / regular / unknown
- sugarLevel：none / low / regular / high / unknown / notApplicable
- sizeBucket：small / regular / large / unknown
- portionRange 或结构份数区间
- source：built_in / user_confirmed / inferred
- confidence
- matchedBy
- useCount
- createdAt / updatedAt
- schemaVersion / policyVersion

如果某字段不适用，要使用 `notApplicable`，不能与 `unknown` 混淆。

## 匹配顺序

1. 用户本地已确认的“品牌 + 标准化商品名”。
2. 用户本地无品牌商品别名。
3. 内置精确名称/别名。
4. 高质量 contains/fuzzy 候选。
5. 类别关键词候选。
6. unmatched。

不要沿用“confidence >= 0.5 就自动添加”的单一规则。建立集中配置的置信度策略：高置信度自动填入、中置信度等待确认、低置信度手动归类。

## UI要求

- 未识别项原地显示“暂时无法准确识别”，不能消失、记零或阻止保存其他已识别菜品。
- 点击后打开轻量选择器；先选大类，再只显示该类别适用字段。
- 奶茶/咖啡显示糖型和杯型。
- 普通食品显示份量；对汉堡/三明治等条件食品，可补充做法和酱料。
- 用户保存前展示“本次估算将如何计入饮食结构”。
- 用户可以编辑、删除本地记忆。

## 数据边界

- 用户纠正不能修改 `GuidelinePolicy` 或内置种子库。
- 本地记忆影响以后匹配和估算，不直接把食品标记为健康。
- 数据清除、导出和数据库升级必须覆盖新表/新字段。

## 必测示例

1. `霸王茶姬 + 青青糯山`：没有内置别名时进入确认；用户选奶茶/常规糖/大杯后保存；再次出现直接复用且可编辑。
2. `肯德基 + 香辣鸡腿堡`：归为汉堡/油炸或信息不足，能够记录但不主动推荐。
3. `巴斯克 小份`：归为甜品、小份、高糖风险候选。
4. `奶油蛋糕 30寸`：不得把“30寸”机械映射成个人一餐的大份精确摄入；提示可能是多人分享并要求确认本次实际食用份量。
5. 完全未知商品：保留 unknown，不记零、不进推荐。
6. 相同商品不同品牌：不能互相覆盖。

## 验收标准

- 重启 App 后用户确认结果仍可复用。
- 删除本地画像后恢复到普通匹配流程。
- 旧数据库无损升级。
- 高/中/低置信度各有正例、反例和边界测试。
- 无网络时全流程可用。
- 静态检查和完整测试全绿。

完成后提交数据字典、迁移说明、UI流程截图、测试结果和遗留风险，等待产品验收。
```

## P3：健康安全门与 7/28 天推荐闭环

### 给开发团队的 Prompt

```markdown
你现在负责餐盘 V1 的“确定性健康安全门与 7/28 天推荐闭环”。

先阅读 `AGENTS.md`、当前 RecommendationEngine、BalanceLedger、dietary_guidelines.json、P2 的商品语义画像和所有推荐测试。

## 核心原则

AI 不参与 V1。食品事实与健康政策必须分层：商品画像提供“它是什么、怎么做、糖型和份量”；GuidelinePolicy 决定“是否允许主动推荐、如何影响 7/28 天结构”。

## 任务

1. 建立集中、可版本化的 RecommendationEligibilityEvaluator，先过滤、后排序。
2. 明确三种状态：
   - eligible：允许主动推荐。
   - conditional：满足已确认条件后可推荐。
   - ineligible：可记录但不主动推荐。
3. 至少覆盖：
   - 酒精：ineligible。
   - 含糖饮料、已知含糖奶茶：ineligible。
   - 无糖奶茶也不能自动等同健康；根据配料信息不足保持 conditional 或 ineligible。
   - 明确油炸、高盐、高糖：ineligible。
   - 配方不明的汉堡/三明治：conditional，不主动推荐。
   - 用户确认非油炸蛋白 + 主食 + 蔬菜 + 无/少酱：可按结构事实变为 eligible。
4. 不允许只信任 seed 数据里的 `recommendable`；启动或测试时检查它与风险标签、类别和政策是否冲突。
5. 实现 7 天高风险暴露提醒：
   - 最近 7 天第一次记录含糖奶茶：正常记录，不惩罚。
   - 同一滚动 7 天再次记录：保存后温和提示“最近7天已经记录过一次含糖奶茶，下次要不要优先选不另外加糖或小杯？”
   - 提供“记住下次偏好”和“本周不再提醒”。
   - 对油炸、酒精等风险族群使用独立 exposure key；没有无糖替代的食品不要显示错误替代文案。
6. 增加 28 天趋势层：用于展示结构趋势和推荐背景，不把 28 天平均强行摊到单餐。
7. 每条推荐输出机器可读 reason code、policyVersion 和用户可读解释。
8. 对“没有记录的日子”保持未知，不当作零摄入。

## 验收场景

- 已知酒、含糖饮料、炸鸡、薯条在任何模式下都不会进入主动推荐。
- 条件健康汉堡只有在必要事实确认后才可进入候选。
- 同周第二次奶茶提醒不会阻止保存，不使用羞辱措辞。
- 关闭某类提醒只影响提示，不改变结构计算和安全门。
- 7 天与 28 天窗口跨月、缺失日、修改历史记录和删除记录后均可重算。
- 推荐原因与实际选择一致，不能声称“已优先清淡”却输出高盐/油炸菜。
- 规则冲突测试、属性测试、边界测试和确定性仿真全绿。

## 不做

- 不在线查配料。
- 不根据用户常吃某食品修改全局健康规则。
- 不新增精确热量界面。

完成后提交规则决策表、reason code 表、测试矩阵、7/28 天仿真结果和产品待确认项。
```

## P4：真实识别验收集与 OCR 链路加固

### 给开发团队的 Prompt

```markdown
你现在负责餐盘 V1 的“真实识别验收集与 OCR 全链路加固”。

先阅读 `AGENTS.md`、P2/P3 交接文档、OcrPipeline、Android 原生 OCR、DishMatcher 和识别结果编辑页。

## 目标

不追求每个商品都自动识别；追求高置信度结果可靠、中低置信度不欺骗、纠错足够轻。

## 建立验收集

在 `test/fixtures/recognition_acceptance/` 建立脱敏、可重复测试的数据集和 manifest。不得提交包含姓名、电话、地址、订单号的原始截图。

验收集至少覆盖：

- 美团、淘宝闪购/饿了么、京东外卖等不同截图布局。
- 菜名、规格、加料、价格、数量、优惠信息混排。
- 品牌营销名：青青糯山等。
- 连锁快餐：香辣鸡腿堡、套餐、可乐、薯条。
- 甜品份量：小份巴斯克、多人蛋糕。
- 奶茶糖型和杯型：无糖/不另外加糖/三分糖/正常糖、大中小杯。
- OCR错字、空格、括号、乘号、数量后缀。
- 完全未知商品。

## 分层指标

分别统计，不得只报一个“准确率”：

1. OCR 文本召回。
2. 商品行解析召回和误报。
3. 大类归类正确率。
4. 糖型/杯型/份量抽取正确率。
5. 高置信度自动接受的错误率。
6. unknown 率。
7. 用户确认后再次复用成功率。

## 产品规则

- 价格、优惠、配送费、数量不能误识别成菜品。
- OCR失败、超时、空结果时保留手动添加入口。
- 一张图部分成功时允许保存已确认项，并逐项处理未知项。
- 原图只保留完成识别所需时间，按现有缓存策略及时清理。

## 验收标准

- 每个历史 Bug 都固化为回归测试。
- 高置信度自动接受不得出现已知危险误判样例。
- 所有 unknown 都有明确 UI 和手动修正路径。
- 同一 fixture 重复运行结果稳定。
- 单元/组件测试全绿，并给出 Android 真机手测清单。

完成后提交验收集说明、指标基线、失败样本分类和下一轮数据补齐建议。
```

## P5：Android 真机、包体、图标与 Widget

### 给开发团队的 Prompt

```markdown
你现在负责餐盘 V1 的“Android 发布质量与真机验收”。

先阅读 `AGENTS.md`、P4 真机手测清单、AndroidManifest、Gradle 配置、OCR 原生实现、Widget Provider 和当前发布产物。

## 原则

先测量，再优化。当前约 88.8MB 的 release APK 不能仅凭感觉归因于代码、菜库或 OCR 模型。

## 任务 A：构建与体积

1. 记录 Flutter/Gradle/JDK/Android SDK 版本。
2. 生成可复现 release 构建，使用构建分析和 APK Analyzer 列出体积前 20 项。
3. 区分：Dart AOT、各 ABI native 库、ML Kit OCR、资源、字体、调试符号、重复资产。
4. 比较：
   - universal APK
   - split-per-abi APK
   - Android App Bundle
5. 只实施有证据、不会破坏国内 Android 兼容性的优化。
6. 不要未经小米真机验证就把内置中文 OCR 改成依赖 Google Play 服务动态下载。

## 任务 B：真机核心链路

在用户的小米手机上逐项验证并保留证据：

- 首次安装、新手引导、杀进程重启。
- 从外卖截图分享至餐盘。
- App内拍照和相册选择。
- OCR成功、部分成功、失败、超时。
- 手动纠正、本地记忆、再次识别复用。
- 保存后首页、历史、宠物和推荐同步更新。
- 无网模式。
- 数据库从旧 beta 升级且用户数据不丢失。

## 任务 C：图标与 Widget

1. 检查当前 launcher icon 是否仍为默认 Flutter 图标；接入用户最终确认的自适应图标、前景层、背景色和圆形裁切预览。
2. 核对 Widget Receiver、provider XML、尺寸、exported 属性、updatePeriod、点击 Intent。
3. 在小米桌面真实验证：
   - 系统小组件列表能找到餐盘。
   - 小/中尺寸能添加。
   - 记录后刷新。
   - 杀进程、重启手机后仍显示。
   - 点击能打开正确页面。
4. 如果小米入口与 Pixel 模拟器不同，更新用户引导，不要把厂商入口差异误判为代码缺失。

## 发布护栏

- 设置正式 applicationId、版本号和签名流程；签名密钥不得提交仓库。
- 检查 release 日志、权限、备份策略、隐私说明和崩溃降级。
- 不加入 AI、社区或额外联网功能。

## 验收标准

- release 构建可在目标小米真机安装、升级、启动。
- 核心闭环手测全部通过并有截图/日志。
- Widget 在小米真机完成发现、添加、刷新、重启验收。
- 输出体积构成和优化前后对比；若仍较大，能够解释不可删除部分。
- 静态检查和完整测试全绿。

完成后提交 `dev-docs/android-release-candidate-report.md`、构建产物 SHA-256、真机验收矩阵和遗留风险。
```

## P6：封闭测试与 V1 封版

### 给开发团队的 Prompt

```markdown
你现在负责餐盘 V1 的“封闭测试、缺陷收敛与封版”。

先阅读 `AGENTS.md` 和 `dev-docs/android-release-candidate-report.md`。本阶段禁止增加新功能，只修复阻断发布的问题。

## 封闭测试目标

用 5–10 名真实外卖用户进行 7 天试用。测试数据默认留在用户本机；问题反馈必须脱敏。

## 需要记录的本地或人工指标

- 分享截图后完成一次记录的成功率。
- 单次记录需要的确认次数和耗时。
- 自动分类、候选确认、手动归类、完全放弃的比例。
- 同一商品第二次出现时本地画像复用成功率。
- 高置信度错误接受数。
- 未识别项被静默忽略数，目标必须为 0。
- 已知不健康食品被主动推荐数，目标必须为 0。
- 崩溃、卡死、数据库丢失、Widget失效次数。
- 用户是否看得懂 7 天建议与 28 天趋势。

## 缺陷分级

- P0：崩溃、数据丢失、无法记录、危险食品主动推荐、旧库升级失败。
- P1：主要截图无法识别且无降级、推荐理由错误、Widget核心失效。
- P2：文案、布局、低频兼容性和轻微性能问题。

## 封版规则

1. P0 必须清零。
2. P1 必须清零或有产品经理批准的明确降级。
3. 每个修复必须有复现步骤和回归测试。
4. 不得用扩大识别范围的临时模糊规则掩盖问题。
5. 更新 README，使其与真实功能一致，删除 mock、双端首发等过时描述。
6. 生成版本说明、隐私说明、已知限制、安装说明和回滚说明。
7. 重新执行 release 构建、静态检查、完整测试和小米真机冒烟。

## 最终交付

- V1 release APK/AAB 及 SHA-256。
- `dev-docs/v1-release-acceptance.md`。
- 完整测试和真机证据。
- 已知限制列表。
- V1.1 候选需求池，但不得在本阶段实现。

完成后等待产品 Owner 做最终发布决定，不要自行上传应用商店。
```

## 4. V1.1 以后再评估

只有 V1 封闭测试证明“未知商品比例”或“重复人工归类成本”仍然显著影响核心体验时，才进入 V1.1 评估：

- 文本 AI 仅作为未知商品的低频候选生成器。
- 只发送脱敏 OCR 文本，不上传截图。
- AI 不得绕过确定性健康安全门。
- 社区纠错必须有用户同意、审核、版本和回滚机制。
- 先算调用成本、隐私和误判收益，再立项。

2. 判断通过、带条件通过或退回。
3. 更新需求和风险，不让开发团队自行扩大范围。
4. 只有本阶段通过后，才发下一阶段 Prompt。
