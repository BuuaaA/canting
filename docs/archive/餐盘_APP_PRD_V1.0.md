## 一、概述

### 1.1 产品概述及目标

#### 1.1.1 背景介绍

当代都市年轻人中，有相当一部分人群日常不开火做饭，一日三餐 90% 以上依靠外卖。这类人群开始注重健康饮食，但面临三个核心痛点：

1. **缺少概念**：不知道"健康饮食"到底是什么结构，对《中国居民膳食指南》没有体感
2. **缺少记录动力**：薄荷健康等传统工具需要手动输入、精准到克，门槛太高，坚持不下来
3. **缺少行动指引**：就算知道自己吃得不健康，也不知道下一顿该怎么调整

现有市场上的饮食管理 APP 普遍以"卡路里/克重计算"和"减肥"为核心，容易给用户造成焦虑感和负罪感，且外卖场景没有被深度优化。

#### 1.1.2 产品概述

「餐盘」是一款**面向外卖依赖型都市年轻人的轻干预饮食结构健康管理 APP**。

核心逻辑：用户分享外卖订单截图给 APP，本地自动识别菜品并分析当日饮食结构（以"份数"而非"克重"呈现），并推荐下一餐的时间和类型建议，引导用户逐步向更健康的饮食结构靠拢。

用户可选择一只像素风电子宠物（猫/狗/仓鼠），宠物的活力状态和成长阶段与用户的膳食结构记录实时关联。宠物可通过桌面小组件常驻手机主屏，既是装饰也是快速打开餐盘的入口。

**产品定位一句话**：外卖党的轻量饮食结构助手——不计算卡路里，只帮你把结构吃对。

#### 1.1.3 产品目标

**用户目标**：
- 让用户 3 秒内知道"今天吃得怎么样"
- 让用户知道"下一顿该吃什么、什么时候吃"
- 不焦虑、不负罪，温和改善饮食结构
- 有一只可爱的电子宠物陪伴，让记录不枯燥

**商业模式**：开源免费，个人开发者模式，全本地处理，零服务器成本。

**V1.0 成功指标**：

| 指标 | 定义 | 目标值 |
|------|------|--------|
| 次日留存率 | 安装后第2天仍打开APP的用户比例 | ≥ 30% |
| 日均记录餐次 | 每活跃用户日均记录的餐食次数 | ≥ 1.5 次/人 |
| 推荐点击率 | 推荐详情页中外卖平台跳转按钮点击率 | ≥ 20% |
| 7日留存率 | 安装后第7天仍打开APP的用户比例 | ≥ 15% |
| OCR识别成功率 | 分享截图后成功识别出至少1道菜的比例 | ≥ 85% |

**电子宠物成效指标**（观测指标）：

| 指标 | 定义 | 目标值 |
|------|------|--------|
| 小组件添加率 | 安装后7天内添加桌面小组件的用户占比 | ≥ 15% |
| 宠物互动率 | 每日执行"摸摸头"操作的用户占 DAU 比例 | ≥ 20% |
| 进化达成率 | 注册7天内宠物进化到幼年阶段的用户比例 | ≥ 40% |

#### 1.1.4 目标用户

**核心人群**：
- 年龄：20-35 岁
- 城市：一二线城市
- 职业：白领/互联网从业者
- 特征：一日三餐 90% 以上靠外卖，开始关注健康但缺少知识和行动力

**典型用户画像 1——忙碌的互联网打工人**：
- 小李，28岁，互联网公司运营
- 三餐全靠外卖，偶尔自己煮个面
- 知道要多吃蔬菜，但点外卖时总忘了
- 试过薄荷健康，记了两天就嫌麻烦放弃了
- 希望有个简单的工具提醒自己吃得健康一点

**典型用户画像 2——注重身材的年轻女性**：
- 小王，25岁，设计师
- 外卖为主，偶尔去健身房
- 不追求减肥，但想保持健康的饮食习惯
- 不喜欢卡路里计算工具，觉得太焦虑
- 希望知道"大概怎么吃比较健康"就够了

### 1.2 名词解释

| 名词 | 解释 |
| ---- | ---- |
| 份数 | 膳食结构的计量单位。1 份 = 一定量的某类食物（如 1 份蔬菜 = 100g，1 份主食 ≈ 50g 生重碳水） |
| 膳食结构 | 各类食物（谷薯/蔬菜/水果/蛋白质/大豆坚果/油脂）的摄入比例和总量 |
| 轻干预 | 不追求精确到克的管理，只做方向性的温和引导和提醒 |
| OCR | 光学字符识别，从图片中提取文字 |
| 分享扩展 | iOS Share Extension / Android Intent Filters，用户从系统分享面板调起 APP |
| 本地通知 | 不依赖后端推送服务，APP 本地调度的通知 |
| 活力值 | 电子宠物的即时状态指标（0-100），反映近期饮食质量 |
| 成长值 | 电子宠物的累计成长进度，只增不减，触发进化 |
| L1 分类 | 膳食结构的一级分类，共 6 大类（谷薯/蔬菜/水果/蛋白质/大豆坚果/油脂） |
| L2 菜品库 | 外卖常见菜品的结构化数据库，每道菜映射到 L1 分类和份数 |
| cn-food-mcp | 开源中国食物营养数据库（MIT 协议），约 1725 种食材，用于 L2 菜品标注参考 |
| 油脂修正系数 | 不同烹饪方式的油脂含量修正倍数，用于估算外卖菜品的油脂份数 |

### 1.3 用户角色与权限

V1.0 只有一种用户角色：**普通用户**。无需注册登录，下载即用，所有数据本地存储。

| 普通用户 | 所有功能：记录餐食、查看结构、获取推荐、设置个人信息、管理宠物、数据导出 |

## 二、产品描述

### 2.1 产品定位与差异化

| 维度 | 餐盘（我们） | 薄荷健康 | 小卡健康 | 美团 Mia |
|------|------------|---------|---------|---------|
| 核心定位 | 外卖用户饮食结构轻干预+电子宠物 | 体重管理/减脂平台 | AI 饮食记录工具 | 外卖 AI 减脂助手 |
| 价值主张 | 结构尽量健康，不焦虑，有宠物陪 | 精准记录，科学减重 | AI 让记录更简单 | 吃外卖也能瘦 |
| 记录方式 | 分享截图自动识别 | 搜索/扫码/拍照 | 多模态（拍/说/扫/截图） | 自动同步美团订单 |
| 分析单位 | 份数/结构完成度 | 克重/卡路里 | 克重/卡路里 | 减脂目标导向 |
| 推荐类型 | 下一餐时间+菜品类型+搜索跳转 | 食谱推荐 | AI 搭子推荐 | 外卖搭配+一键下单 |
| 粘性机制 | 电子宠物+桌面小组件 | 社区+打卡 | AI 对话 | 交易闭环 |
| 商业模式 | 开源免费 | 会员+电商+服务 | 会员制 | 交易导流（推测） |

**核心差异化**：
1. 外卖场景极致深耕（所有竞品都把外卖当补充场景）
2. 结构导向 + 零焦虑体验（竞品都以卡路里/克重为核心）
3. 下一餐时间+内容双推荐（没人做透时间推荐）
4. 全本地处理，隐私友好
5. 电子宠物+桌面小组件增加获客吸引力和用户粘性

### 2.2 整体页面结构

```
启动页 → 欢迎页 → 初始设置（6步） → 首页
                                      │
                          ┌───────────┼───────────┐
                          ▼           ▼           ▼
                       🏠今日(含宠物)  📅记录(含宠物状态)  👤我的(含宠物管理)
```

底部 Tab 导航（3 个）：
1. **🏠 今日** — 首页，宠物展示区 + 膳食结构 + 记录入口 + 下一餐推荐
2. **📅 记录** — 历史记录，日历视图（圆点反映宠物活力状态）
3. **👤 我的** — 个人设置 + 我的宠物管理 + 数据管理

### 2.3 核心使用流程

```
用户点外卖 → 截图订单 → 分享给「餐盘」
     │
     ▼
餐盘分享扩展（后台处理，不跳转主APP）
     │
     ├── 本地 OCR 识别菜名
     ├── 菜品映射（L2 菜品库匹配 → L1 分类份数）
     ├── 保存到本地 SQLite 数据库
     ├── 计算当日膳食结构
     ├── 计算下一餐推荐（时间 + 类型）
     ├── 更新宠物活力值和成长值
     └── 触发小组件刷新
     │
     ▼
本地通知（通知栏）：
  ✅ 已记录午餐 · 黄焖鸡米饭
  🐱 小挑食：嗯嗯，吃得不错嘛～
  ⏰ 下一餐 18:30 · 多吃点蔬菜吧
     │
     ▼
（用户继续刷外卖APP，不被打断）
点击通知 → 打开餐盘APP → 查看详情/修改
桌面小组件实时展示宠物状态，点击直接打开APP
```

### 2.5 技术架构

**技术栈**：Flutter + 原生混合

- UI 层：Flutter（一套代码双平台）
- OCR + 分享扩展：各平台原生实现，通过 Method Channel 与 Flutter 层通信
- 桌面小组件：iOS WidgetKit (Swift) / Android AppWidget (Kotlin)，原生实现（V1.1）
- 数据层：本地 SQLite 数据库，App Group / 共享存储实现扩展与主 APP 数据共享
- 宠物 sprite 动画：`Image.asset` + `AnimationController` 逐帧切换

**OCR 方案**：

| 平台 | OCR 方案 | 说明 |
|------|---------|------|
| iOS | Vision 框架 | 系统自带，零依赖，完全离线 |
| Android | PaddleOCR Lite | 中文准确率高，Apache 2.0 协议，包体积增量约 10MB+ |

**底层食材数据**：cn-food-mcp（MIT 协议，1725 种中国食物营养数据）
- 仅作为 L2 菜品人工标注的参考依据
- 不打包进 APP，运行时不依赖
- 标注完成后可脱离

**像素美术资源**：AI 生成（Stable Diffusion，开源可商用）+ 手动微调，约 100 帧素材

## 三、功能需求

### 3.1 食物数据库与菜品映射

#### 3.1.1 数据分层设计

采用三层架构，核心原则：**展示用份数，不展示精确营养素**。

```
L1：膳食结构分类（展示层）
  ↓ 映射
L2：外卖菜品库（识别层）
  ↓ 标注参考
cn-food-mcp 原材料数据（标注工具层，非运行时依赖）
```

#### 3.1.2 L1 膳食结构分类

#### 3.1.4 菜品匹配引擎

**匹配优先级**：
1. **精确匹配**：OCR 文本与菜名或别名完全一致
2. **包含匹配**：OCR 文本包含菜名（或菜名包含OCR文本）
3. **模糊匹配**：相似度 > 0.7 的菜名（编辑距离算法）
4. **关键词归类**：匹配不到具体菜品时，根据关键词归类到 L1 分类

**匹配结果**：
```dart
class DishMatchResult {
  final Dish dish;
  final double confidence;   // 匹配置信度 0-1
  final MatchMethod method;  // exact/contains/fuzzy/keyword
}
```

**未匹配处理**：
- 如果一道菜完全匹配不到，展示为"未知菜品"，用户可手动选择分类和份数
- 未匹配的菜品不影响其他菜品的记录

### 3.3 每日建议摄入量计算

#### 3.3.1 计算逻辑

**核心原则：基于膳食指南权威数据，按能量水平查表，不做过度精确的动态计算。**

**第一步：基础代谢率（BMR）** — Mifflin-St Jeor 公式
- 男：BMR = 10 × 体重(kg) + 6.25 × 身高(cm) - 5 × 年龄 + 5
- 女：BMR = 10 × 体重(kg) + 6.25 × 身高(cm) - 5 × 年龄 - 161

**第二步：总能量消耗（TDEE）**
- TDEE = BMR × 活动系数
  - 久坐：1.2
  - 轻度活动：1.375
  - 中等活动：1.55
  - 重度活动：1.725

**第三步：匹配膳食指南能量档位**
- 将 TDEE 就近归入 5 个档位：1600 / 1800 / 2000 / 2200 / 2400 kcal
- 从膳食指南数据表中读取对应档位的各分类推荐量
- 数据来源：`assets/data/dietary_guidelines.json` → `daily_intake_recommendation.by_energy_level`

**膳食指南推荐份数表**：

| L1 分类 | 1600kcal | 1800kcal | 2000kcal | 2200kcal | 2400kcal |
|---------|----------|----------|----------|----------|----------|
| 谷薯类 | 4 份 | 5 份 | 5 份 | 6 份 | 6 份 |
| 蔬菜类 | 4 份 | 4.5 份 | 5 份 | 5 份 | 5 份 |
| 水果类 | 2 份 | 2.5 份 | 3 份 | 3 份 | 3.5 份 |
| 蛋白质（肉蛋） | 3 份 | 3.5 份 | 4 份 | 4.5 份 | 5 份 |
| 奶类 | 2 份 | 2 份 | 2 份 | 2 份 | 2 份 |
| 大豆 | 1 份 | 1.5 份 | 2 份 | 2 份 | 2 份 |
| 坚果 | 1 份 | 1 份 | 1 份 | 1 份 | 1 份 |

**第四步：饮食目标微调**
- 均衡饮食：不调整
- 多吃蔬菜：蔬菜目标 × 1.2
- 多蛋白质：蛋白质目标 × 1.2
- 控制主食：谷薯目标 × 0.8

#### 3.3.2 特殊规则

**坚果的周目标机制**：
- 坚果不设每日强制目标，设每周目标（50-70g ≈ 5-7 份）
- 当日坚果进度不计入"今日完成度"的核心计算
- 每周累计追踪，达标给宠物额外成长值奖励

**食物多样性目标**：
- 每日：≥ 12 种食物
- 每周：≥ 25 种食物
- 作为鼓励性指标，不影响核心结构评分

#### 3.3.3 计算时机

- 初始设置完成后计算一次
- 用户修改个人信息（体重/身高/年龄/活动量/饮食目标）后重新计算
- 计算结果写入用户档案，不实时计算

#### 3.3.3 用户故事

- 作为用户，我希望 APP 根据我的身体数据给出合适的目标，以便参考更准确

### 3.5 餐食记录

#### 3.5.1 记录数据结构

```dart
class MealRecord {
  final String id;
  final DateTime mealTime;      // 用餐时间
  final MealType type;          // 早餐/午餐/晚餐/加餐
  final List<MealDish> dishes;  // 菜品列表
  final String? note;           // 备注
  final DateTime createdAt;
  final DateTime updatedAt;
}

class MealDish {
  final String dishId;          // 关联 L2 菜品ID
  final String dishName;        // 菜名（快照，防止后续菜品库变动）
  final String size;            // small/regular/large
  final Map<String, double> servings; // 各分类份数快照
  final double confidence;      // 识别置信度（手动添加为 1.0）
}
```

#### 3.5.2 添加记录方式

V1.0 支持 3 种添加记录的方式：

| 方式 | 入口 | 适用场景 |
|------|------|---------|
| 截图识别 | 分享扩展 / APP 内选图 | 点外卖时快速记录 |
| 手动添加（简单模式） | 首页「+」→ 手动添加 | 自己做饭、食堂、外食 |
| 手动添加（详细模式） | 简单模式下展开「详细填写」 | 想精确记录克数 |

##### 手动添加：简单模式

**3 步完成**：
1. 选餐次（早餐/午餐/晚餐/加餐）
2. 搜菜名（从 L2 菜品库搜索，支持模糊匹配，用户自定义菜品优先展示）
3. 调份量（小份/常规/大份 三档，默认常规）

点击「添加」即完成。

##### 手动添加：详细模式

在简单模式基础上，展开「详细填写」可看到：

| 字段 | 类型 | 说明 |
|------|------|------|
| 菜名 | 文本 | 可手动输入，不一定从库里选 |
| 分类 | 多选 | 谷薯/蔬菜/水果/蛋白质/大豆坚果（一道菜可跨多个分类） |
| 重量(g) | 数字输入 | 用户自己估重，**选填** |
| 份量 | 滑块/数字 | APP 自动根据重量推算，用户也可以手动调整 |
| 自制餐食 | 开关 | 标记这是自己做的饭 |
| 备注 | 文本 | 选填 |

**核心交互：重量 ↔ 份数 双向联动**
- 用户输入重量 → APP 根据该菜品的标准份量自动推算份数
- 用户调整份数 → APP 反推对应的重量
- 两种方式用户任选一种，实时联动

##### 用户自定义菜品

- 用户手动输入的、不在 L2 库里的菜，会保存为「我的菜品」
- 下次搜索时优先展示在顶部
- 记录使用次数，常用的排前面
- 可在设置中管理「我的菜品」

#### 3.5.3 用户数据反馈机制（数据飞轮）

**核心理念：用户每一次手动填写重量，都是一次标注。积累得多了，我们的菜品份数估算就越来越准。**

**V1.0：个人级优化（纯本地）**
- 记住用户对某道菜的份量偏好（比如用户总把宫保鸡丁调成大份，下次默认就是大份）
- 用户常吃的自定义菜品，下次输入时自动提示
- 所有数据纯本地存储，不上传

**V1.1：匿名聚合优化（可选）**
- 如果用户开启「帮助改进产品」开关
- 匿名上传菜名 + 重量 + 份数调整数据
- 服务端聚合后优化 L2 菜品库的标准份量
- 定期更新到 APP 菜品库

**V2.0：推荐个性化**
- 基于用户历史记录分析口味偏好
- 在结构优化的前提下，优先推荐用户爱吃的菜
- 越用越准

**隐私设计**：
- 默认纯本地，数据不出手机
- 上传是可选开关（默认关闭）
- 上传数据匿名化：不含用户ID、不含精确时间戳、不含位置信息
- 用户可以随时导出和删除自己的所有数据

#### 3.5.4 记录详情页

**展示内容**：
- 餐次 + 时间
- 菜品列表（可左滑删除）
- 这顿饭的结构贡献（各分类份数）
- 备注（可编辑）
- 「删除此记录」按钮（底部）

**操作**：
- 点击菜品 → 修改分量
- 左滑菜品 → 删除
- 删除记录 → 二次确认弹窗

#### 3.5.4 删除记录的影响

- 从当日膳食结构中扣除该餐的所有份数
- 宠物活力值回退（按该餐的贡献比例）
- 成长值不回退（成长值只增不减）
- 推荐重新计算

#### 3.5.5 分量调整

- 每道菜可选择：小份 / 常规 / 大份
- 默认值来自 L2 菜品库的 sizeDefault
- 调整后实时更新份数计算

#### 3.5.6 前置/后置条件

- 前置条件：用户已完成初始设置
- 后置条件：记录写入数据库，当日结构重新计算，宠物状态更新，推荐更新

#### 3.5.7 异常与边界

- 删除最后一条记录：首页回到空状态
- 跨日期添加记录：可以添加过去的记录，但只能添加最近 7 天内的
- 重复添加：允许添加相同菜品（可能点了两份）

### 3.6 推荐系统

#### 3.6.1 推荐目标与两阶段设计

**推荐核心目标：通过动态调整一日三餐的菜品类型，让用户的膳食结构逐步接近中国居民膳食指南的推荐。**

不追求精确最优，只给方向性引导。核心是告诉用户"下一顿大概往什么方向调整"。

**两阶段设计**：

| 阶段 | 名称 | 核心逻辑 | V1.0 状态 |
|------|------|---------|-----------|
| 第一阶段 | 结构优化推荐 | 根据当日膳食缺口，推荐能弥补缺口的菜品类型 | ✅ V1.0 实现 |
| 第二阶段 | 口味匹配推荐 | 在满足结构优化的前提下，优先推荐用户爱吃的菜 | 🔜 V1.1 实现（架构预留） |

**第一阶段（V1.0）：结构优化**
- 输入：当日已摄入的膳食结构 + 膳食指南目标
- 计算：各分类的缺口
- 输出：下一顿应该侧重什么类型的菜
- 特点：规则驱动，不需要用户历史数据

**第二阶段（V1.1+）：口味匹配 + 数据驱动**
- 输入：用户历史记录 → 分析口味偏好（常点什么菜、哪些菜被标记"喜欢"）
- 约束：在满足结构优化的前提下
- 输出：推荐用户既爱吃、又能改善结构的菜
- 特点：越用越准，数据驱动迭代
- V1.0 只做架构预留：记录用户行为数据、本地积累偏好

#### 3.6.2 下一餐时间推荐

**规则**：
- 找到距离当前时间最近的下一个饭点（早/午/晚）
- 基于用户设置的作息时间
- 如果已经过了所有饭点（晚上 10 点后），显示"明天早餐"

**示例**：
- 当前 10:00 → 下一餐：午餐 12:30
- 当前 14:00 → 下一餐：晚餐 18:30
- 当前 22:30 → 下一餐：明天早餐 7:30

#### 3.6.3 下一餐类型推荐

**算法逻辑**：
1. 计算当日各分类的剩余缺口 = 目标份数 - 已摄入份数
2. 排除已经达标的分类
3. 按缺口大小排序，取缺口最大的 1-2 个分类
4. 结合餐次特性调整（早餐通常是主食+蛋白，午餐晚餐更均衡）
5. 输出推荐类型 + 推荐理由

**推荐类型定义**：

| 推荐类型 | 触发条件 | 文案示例 |
|---------|---------|---------|
| 多吃蔬菜 | 蔬菜缺口最大 | 「今天蔬菜吃得少，下一顿多加点青菜吧～」 |
| 多点蛋白质 | 蛋白质缺口最大 | 「可以来点鱼或鸡肉，补充蛋白质」 |
| 控制主食 | 主食已经超标 | 「主食已经够啦，下顿少点一点饭」 |
| 均衡搭配 | 各分类都差不多 | 「吃得挺均衡的，继续保持～」 |
| 加点水果 | 水果缺口大且快到下午 | 「下午啦，来份水果当加餐？」 |

**推荐菜品示例**：
- 推荐详情页展示 3-5 道推荐菜品
- 从 L2 菜品库中筛选符合推荐类型的菜品
- 优先选择常见的、容易在外卖平台搜到的菜
- 每次刷新可随机轮换（增加丰富感）

### 3.7 识别系统

#### 3.7.1 识别入口

V1.0 支持两种识别入口：

1. **分享扩展**（核心入口）：用户在外卖 APP 截图 → 系统分享面板 → 选择「餐盘」→ 后台识别 → 发通知
2. **APP 内识别**（补充入口）：首页「+ 添加记录」→ 「拍照识别」/ 「从相册选择」→ 识别 → 确认保存

#### 3.7.2 iOS 分享扩展 + Vision OCR

**技术实现**：
- Share Extension 扩展
- 使用 iOS 系统 Vision 框架进行文字识别
- 通过 App Group 共享 SQLite 数据库与主 APP 通信
- 识别完成后发送本地通知

**识别流程**：
```
用户分享截图 → Share Extension 启动
  → Vision 框架识别文字
  → 菜品匹配引擎匹配 L2 菜品
  → 写入共享数据库（App Group）
  → 更新今日结构 + 宠物状态
  → 调度本地通知
  → 扩展结束（用户停留在原外卖 APP）
```

**通知**：
- 识别成功：「✅ 已记录 {餐次} · {主要菜名} + {宠物台词}」
- 识别失败：「🤔 这张图没认出来，打开 APP 手动添加吧」

#### 3.7.3 Android 分享扩展 + PaddleOCR Lite

**技术实现**：
- Intent Filter 接收图片分享
- 使用 PaddleOCR Lite 进行中文文字识别（离线模型）
- 共享数据库（FileProvider / 内部存储）
- 识别完成后发送本地通知

**识别流程与 iOS 基本一致**。

**模型选择**：
- PaddleOCR Lite 超轻量模型（PP-OCRv4 或更新版本）
- 中文识别优先
- 模型大小约 10MB+，打包进 APK

#### 3.7.4 APP 内识别

**入口**：
- 首页「+ 添加记录」→ 「拍照识别」
- 首页「+ 添加记录」→ 「从相册选择」

**流程**：
1. 拍照或选图
2. 裁剪/确认图片
3. OCR 识别（同分享扩展逻辑）
4. 进入识别结果页
5. 用户确认或修改后保存

#### 3.7.5 识别结果页

**展示内容**：
- 原始图片缩略图
- 识别出的菜品列表（带置信度）
- 每道菜可：修改分量 / 替换菜品 / 删除
- 「+ 添加菜品」手动补充
- 选择餐次和时间
- 「保存记录」按钮

**置信度显示**：
- 高置信度（>0.8）：正常显示
- 中置信度（0.5-0.8）：黄色小标记「可能不太准，点这里修改」
- 低置信度（<0.5）：不自动加入列表，显示在「未识别」区域供用户手动选择

#### 3.7.6 识别成功率指标

- 目标：主流外卖平台（美团/饿了么）订单截图识别成功率 ≥ 85%
- 统计方式：识别出至少 1 道菜即为成功
- 失败原因分析：OCR 识别失败 / 菜名不在 L2 库中 / 匹配算法失效

#### 3.7.7 前置/后置条件

- 前置条件：用户授予图片/相机权限（首次使用时弹窗申请）
- 后置条件：识别结果保存到数据库，更新结构和宠物状态

#### 3.7.8 异常与边界

- 权限被拒绝：引导用户到系统设置开启
- 图片模糊/反光：识别失败，提示「图片不太清晰，试试手动添加」
- 识别结果为空（一道菜都没匹配到）：提示没认出来，提供手动添加入口
- 网络不可用：OCR 完全本地，不影响
- 分享扩展处理超时（>30秒）：保存已识别的部分，发通知说明可能不完整

### 3.8 电子宠物系统

#### 3.8.1 宠物属性

```dart
class Pet {
  final String id;
  final PetType type;         // cat/dog/hamster
  final String name;          // 用户给的名字
  final PetStage stage;       // 幼年/成年/进化形态
  final double vitality;      // 活力值 0-100
  final double growth;        // 成长值 只增不减
  final DateTime createdAt;
  final DateTime lastUpdated;
  final int petCount;         // 今日摸摸头次数
  final DateTime lastPetTime; // 上次摸摸头时间
}
```

#### 3.8.2 活力值计算

**定义**：反映最近 24 小时的饮食质量，范围 0-100，下限 15（永不归零）。

**计算逻辑**：
- 基础分 60 分
- 各分类达标情况加减分：
  - 蔬菜达标（80%-120%）：+15 分
  - 蛋白质达标：+10 分
  - 主食达标：+5 分
  - 水果达标：+5 分
  - 大豆坚果达标：+5 分
- 油脂超标（>150%）：-10 分
- 当日记录 ≥ 2 餐：+5 分（鼓励记录）
- 上限 100，下限 15

**状态映射**：

| 活力值范围 | 状态 | 文案风格 |
|-----------|------|---------|
| 80-100 | 非常开心 | 表扬、夸赞 |
| 60-79 | 还不错 | 鼓励、肯定 |
| 40-59 | 一般 | 温和提醒 |
| 20-39 | 不太开心 | 撒娇、委屈 |
| 15-19 | 蔫蔫的 | 可怜、需要关心 |

**时间衰减**：
- 如果超过 24 小时没有新记录，活力值每天缓慢下降 5 点（最低 15）
- 模拟"饿肚子"的感觉，鼓励持续记录

#### 3.8.3 成长值与进化

**成长值**：
- 每记录 1 餐：+10 点
- 当天饮食结构达标（完成度 > 80%）：额外 +5 点
- 每日上限：+30 点
- 只增不减（即使吃差餐也 +3 保底成长值——记录就有奖励）

**进化阶段**：

| 阶段 | 成长值阈值 | 说明 |
|------|-----------|------|
| 幼年 | 0-49 | 初始形态，小小的 |
| 少年 | 50-199 | 第一阶段进化，稍微长大了 |
| 成年 | 200+ | 最终形态（V1.0 到此为止） |

**进化动画**：
- 达到阈值时触发进化动画
- 全屏展示，宠物从旧形态变到新形态
- 配进化文案和庆祝音效（可选）

#### 3.8.4 摸摸头互动

**规则**：
- 点击宠物触发摸摸头动画和对话气泡
- 冷却时间：4 小时
- 每日上限：3 次
- 每次摸摸头：+1 点成长值（小奖励）

**对话气泡文案**：
- 根据宠物当前状态（活力值）和当日饮食情况动态生成
- 不展开详细的份数数据，用感性的话
- 字数 ≤ 20 字

**文案示例**：

| 场景 | 文案 |
|------|------|
| 蔬菜吃够了 | 「今天有好好吃菜呢～」 |
| 蔬菜不够 | 「想吃菜菜...🥬」 |
| 肉吃多了 | 「肉肉虽好，也要吃菜哦」 |
| 还没记录 | 「今天吃了什么呀？」 |
| 晚上了 | 「晚安，明天也要好好吃饭」 |
| 刚进化完 | 「我长大啦！开心！」 |

#### 3.8.5 宠物与餐食记录的联动

- 添加餐食 → 重新计算活力值 + 成长值
- 删除餐食 → 活力值回退，成长值不回退
- 修改分量 → 重新计算
- 跨日期：活力值取最近 24 小时的加权平均

#### 3.8.6 前置/后置条件

- 前置条件：用户在初始设置中选择了宠物
- 后置条件：宠物状态持久化到数据库

#### 3.8.7 异常与边界

- 宠物名称为空：使用默认名
- 成长值刚好等于阈值：触发进化
- 同一天进化多次：不可能（成长值只增不减，每日有上限）
- 删除所有记录：活力值降到最低 15，成长值保留

### 3.9 历史记录

#### 3.9.1 日历视图

**页面结构**：
- 顶部月份切换（左右箭头 + 月份显示）
- 日历网格（7 列：日一二三四五六）
- 每天一个小圆点，颜色表示当天宠物活力值状态：
  - 绿色：活力值 ≥ 60（吃得不错）
  - 黄色：活力值 40-59（一般）
  - 红色：活力值 < 40（不太好）
  - 灰色：当天无记录
- 点击某一天 → 日详情页

#### 3.9.2 日详情页

**展示内容**：
- 日期 + 当日完成度
- 当日膳食结构（环形图或条形图，复用首页组件）
- 宠物当日状态
- 当日餐食列表（可点击查看详情）
- 「添加记录」按钮（可给过去的日期补录）

#### 3.9.3 补录规则

- 可补录最近 7 天内的记录
- 补录会影响当天的宠物活力值和成长值
- 不影响总成长值的进化判断（成长值按记录时间算，不是按补录时间）

#### 3.9.4 空状态

- 整月无记录：显示空空的日历 + 文案「还没有记录哦，从今天开始吧～」

#### 3.10.2 个人信息编辑

- 身体数据：性别、年龄、身高、体重（可修改）
- 饮食目标：四个选项（可修改）
- 活动量：四个选项（可修改）
- 修改后：重新计算每日建议摄入量 + 重新计算当日结构

**复用组件**：
- 编辑页复用初始设置 Step 1-3 的表单组件
- 预填当前值，用户修改后保存

#### 3.10.3 作息与提醒

- 作息时间：早餐/午餐/晚餐时间 + 日期切换时间
- 通知设置：
  - 识别结果通知：开关（默认开）
  - 通知铃声：跟随系统
  - V1.0 不包含用餐提醒和缺口提醒（V1.1）

#### 3.10.4 外卖平台设置

- 列出所有支持的平台，带开关
- 支持排序（长按拖动）
- 至少选择 1 个平台
- 选中的平台会在推荐详情页显示跳转按钮

#### 3.10.5 数据管理

- **导出数据**：
  - JSON 格式导出（V1.0 必须支持）
  - CSV 格式导出（V1.1）
  - 导出到系统文件管理器 / 分享
- **清除数据**：
  - 二次确认弹窗
  - 清除所有餐食记录 + 重置宠物状态 + 保留用户设置
  - 警告：数据清除后不可恢复（因为是纯本地）

#### 3.10.6 宠物管理

- 宠物信息展示（名字、类型、阶段、活力值、成长值）
- 宠物进化记录
- 重命名宠物
- V1.0 不支持换宠物（V2 图鉴系统）

#### 3.10.7 关于页面

- APP 名称和版本号
- 产品简介
- 开源许可声明（MIT / cn-food-mcp 等）
- 隐私政策（纯本地，不收集任何数据）
- 反馈渠道（邮箱 / GitHub Issues）

### 3.11 通知系统

#### 3.11.1 本地通知方案

V1.0 使用 `flutter_local_notifications` 实现本地通知。

**通知类型**：

| 类型 | 触发时机 | 内容示例 | V1.0 |
|------|---------|---------|------|
| 识别成功通知 | 分享扩展识别完成 | ✅ 已记录午餐 · 黄焖鸡米饭 🐱 小挑食：吃得不错嘛～ | ✅ |
| 识别失败通知 | 分享扩展未识别出菜品 | 🤔 这张图没认出来，打开 APP 手动添加吧 | ✅ |
| 用餐提醒 | 到饭点了提醒吃饭 | 🍽️ 该吃午饭啦，今天想吃什么？ | ❌ V1.1 |
| 缺口提醒 | 晚上了某分类还差很多 | 🥬 今天蔬菜还差一些，晚餐多吃点菜吧 | ❌ V1.1 |

#### 3.11.2 识别成功通知

- 标题：「已记录 {餐次}」
- 内容：「{主要菜名} · {宠物台词}」
- 点击通知 → 打开 APP → 跳转到今日首页
- 通知 ID：按时间戳生成，避免覆盖

#### 3.11.3 权限申请

- 首次使用分享扩展时：不弹窗申请（iOS 系统会自动处理）
- 首次打开 APP 时：在合适的时机引导用户开启通知权限
- 用户拒绝后：在设置页显示「通知未开启」状态，可点击跳转系统设置

### 4.2 性能需求

- 冷启动时间：< 2 秒
- 首页加载：< 500ms（本地数据）
- OCR 识别：单张图片 < 3 秒（中端机型）
- 菜品匹配：< 100ms
- 推荐计算：< 50ms
- APP 包体积：
  - iOS：< 80MB
  - Android：< 100MB（含 PaddleOCR 模型）

### 4.3 安全与合规

- 所有数据本地存储，不上传服务器
- 不收集用户个人信息
- 不请求不必要的权限
- 开源许可声明完整（cn-food-mcp MIT 协议、PaddleOCR Apache 2.0 等）
- 隐私政策说明数据处理方式

### 4.4 统计需求（埋点）

V1.0 纯本地，不做后端埋点。但预留本地事件日志，用于后续版本接入分析（可选）。

**关键本地事件**：
- app_install（首次安装）
- onboarding_complete（初始设置完成）
- meal_record_added（添加记录）
- meal_record_deleted（删除记录）
- ocr_success（识别成功）
- ocr_failure（识别失败）
- recommendation_clicked（推荐跳转）
- pet_patted（摸摸头）
- pet_evolved（宠物进化）
- settings_changed（修改设置）

> 注：V1.0 埋点数据仅存本地，不上传。用户可在设置中选择是否开启。

### 4.5 兼容性

- iOS：支持 iOS 15.0 及以上
- Android：支持 Android 8.0（API 26）及以上
- 屏幕适配：支持各种尺寸的手机屏幕，不做平板适配
- 深色模式：跟随系统，不单独设计
