## 会话 A 指令：菜库蒸馏（数据层）

直接复制以下全文发给会话 A：

```
「餐盘」APP V1.0 · 菜库蒸馏与数据迁移

项目：d:\dev\canting（Flutter + SQLite）
背景：当前 dishes.json 只有 29 道菜（MVP 测试集），推荐系统无米下炊。
目标：蒸馏 nutridata 开源数据仓库的所有菜肴数据，生成尽可能多的高质量菜品标注，
并解决「用户更新 APP 后菜品数据不更新」的问题。

【数据来源与法律红线】
1. 先执行：git clone https://github.com/sunw80910/nutridata_data 到 d:\dev\nutridata_data
   ——必须克隆到 canting 仓库外面，原始数据严禁提交进本仓库（开源仓库会被 DMCA）
2. 蒸馏方式：读取其菜肴/配料构成数据，转换为「我们自己的标注 schema」。
   产出文件是我们自己的衍生物（菜品→分类份数+质量标签），不是复制其数据表
3. 交叉校验：随机抽 20 道菜，用 cn-food-mcp（MIT，npm 包）的原材料营养数据
   做第二来源校验，偏差超过 30% 的菜要人工复核份数

【数据 schema（契约字段，会话 B 依赖，名称不可改）】
每道菜：
{
  "dish_id": "稳定 slug，如 huang_men_ji_mi_fan",
  "dish_name": "黄焖鸡米饭",
  "aliases": ["黄闷鸡米饭", "黄焖鸡"],
  "recommendable": true,          // 是否可进推荐池
  "quality_tags": ["light"],      // whole_grain | light | fried | high_sodium | high_sugar
  "portions_normal": {            // 常规份的分类份数（100g 概念下的交换份折算）
    "grains": 2.0, "vegetables": 0.8, "fruits": 0,
    "protein": 1.5, "protein_soy": 0, "oil": 1.2
  },
  "estimated": false              // true = nutridata 无此菜，AI 按配料估算
}

【蒸馏任务】
1. 解析 nutridata 数据：所有菜肴 → 按配料克重 + 交换份表
   （assets/data/dietary_guidelines.json 的 food_exchange 已有）折算成六类份数
2. 不设道数上限，能蒸馏多少蒸馏多少（预计 1000+）
3. gap-fill：外卖高频菜 nutridata 没有的（黄焖鸡米饭、螺蛳粉、猪脚饭等），
   按菜谱常识估算配料并标注 estimated=true，目标 gap-fill 至少 150 道
4. 垃圾食品与含糖饮品（薯条/炸鸡/可乐/奶茶/汉堡等）：保留进库（识别侧要用，
   用户吃了要能记账），但 recommendable=false + 相应 quality_tags（fried/high_sugar）
5. 质量标签规则：
   - 主料为全谷物/杂豆 → whole_grain（杂粮饭、玉米、燕麦粥、全麦面包）
   - 清蒸/白灼/凉拌/清炒少油 → light
   - 油炸/干锅/红烧/糖醋/拔丝 → fried 或 high_sodium
   - 含糖饮料/甜点 → high_sugar
   - 一道菜可有多个标签；没有任何负面标签且结构合理 → recommendable=true

【数据迁移（用户更新后菜品自动跟上）】
1. dishes.json 顶层加 "schema_version": 2
2. database_helper.dart 实现按 schema_version 触发的增量 upsert：
   - 按 dish_id 对比：新库有旧库无 → 插入；字段变化 → 更新；旧库有新库无 → 不删（保留用户可能的自定义关联）
   - 用户自定义菜品（user_custom_dishes 表）一律不动
3. 播种逻辑从「空表才播」改为「版本变化就 upsert」

【验收标准（全部固化为测试）】
1. 新 dishes.json 通过 schema 校验测试：所有菜必有 dish_id/dish_name/recommendable/quality_tags/portions_normal
2. recommendable=true 的菜不含有 fried/high_sugar 标签（可含 high_sodium？——不可以，一律干净）
3. 不存在全零份数的菜（至少一类 > 0）
4. 垃圾食品抽查：薯条/可乐/炸鸡 均 recommendable=false
5. 杂粮类抽查：杂粮饭/玉米 含 whole_grain 标签
6. 数据库迁移测试：从旧版 29 道种子库升级 → 菜数变为新库数量、用户表数据无损
7. 交叉校验记录：20 道抽检菜的偏差报告，输出到 dev-docs/distill-validation.md
8. flutter analyze 零问题 + flutter test 全过

【文件权限（另一会话在并行改引擎层，严禁越界）】
你只能改：
- assets/data/dishes.json、assets/data/categories.json（如需）
- lib/core/models/ 下菜品相关模型（dish.dart 等）
- lib/data/food_database.dart、lib/data/database_helper.dart（迁移部分）
- pubspec.yaml（如需，只加不改）
- test/ 下你自己新增的测试
严禁碰：lib/core/recommendation_engine.dart、intake_calculator.dart、
lib/ui/recommendation/、lib/pet/、assets/data/dietary_guidelines.json
共享契约：dish 模型上 recommendable、quality_tags 两个字段由你负责添加；
如果发现模型上已有这两个字段（另一会话加了），直接用，不要改名不要删。

【并行在途规则】
跑全量测试时，推荐引擎/指南相关测试若失败且错误信息指向引擎层文件，
标注「另一会话在途」后忽略，只保证你的数据层测试全绿。
真正的全量裁判是之后的集成会话。

【产出报告】
完成后输出：蒸馏菜品总数、分类分布（六类各多少道含>0份数）、
recommendable=true/false 各多少、gap-fill 多少道、抽检偏差报告摘要、
数据库迁移前后对比、analyze/test 结果。
现在开始，全程不要提问，遇到 nutridata 数据格式问题自行判断处理。

## 会话 B 指令：指南重蒸馏 + 滚动调控引擎（引擎层）

直接复制以下全文发给会话 B：

```
「餐盘」APP V1.0 · 指南重蒸馏与滚动平衡推荐引擎

项目：d:\dev\canting（Flutter + SQLite）
背景：当前推荐引擎是「当日缺口补丁」：中午吃炸鸡晚上推蔬菜，第二天就忘了。
产品哲学（用户原话，必须实现）：
  「不是机械的中午吃的不健康晚上就要吃得健康，第二天又正常推了。
   要用算法推荐保证用户未来一个月内的膳食结构是健康的——
   一次不健康的影响要持续传导到后面几天的推荐，最终让长期结构收敛。」

【任务 1：重蒸馏膳食指南 PDF】
源文件：d:\dev\中国居民膳食指南2022.pdf（找不到就停下报告，不要瞎猜数据）
提取并更新 assets/data/dietary_guidelines.json，在现有基础上补：
1. weekly_targets：六类（谷薯/蔬菜/水果/动物蛋白/大豆坚果/油脂）的 7 天目标
   = 单日目标 × 7，按 5 个能量档分别给出
2. 全谷物要求：指南推荐全谷物 50~150g/日 → 换算为 grains 类中 whole_grain
   的日份数下限，用于推荐排序
3. 添加糖：<25g/日（只记录进 JSON，V1.0 不做追踪，注释说明）
4. 周平衡原则字段化：指南明确「一周内平衡即可」，将此原则写入引擎注释与
   recommendations 配置（如 surplus_decay / debt_decay 参数）
5. 油盐上限：油 25~30g/日 → 油脂日目标份数上界；盐不追踪份数，
   用 high_sodium 标签做代理（清淡模式下硬排除）

【任务 2：BalanceLedger 滚动台账（新模块，本次核心）】
新文件 lib/core/balance_ledger.dart：
1. 输入：最近 7 天每类摄入份数（MealRepository 按日查询）+ 周目标
2. 每类维护「盈亏账」：
   - 盈余（吃超，如油脂+2份）：次日衰减 50%（day2 余 1.0、day3 余 0.5…）
   - 欠账（不足，如蔬菜-3份）：衰减 20%/日（长期不足则持续累积影响）
3. 台账输出：每类 {surplus, deficit}，供推荐引擎与文案使用
4. 修正限幅：引擎单餐修正量最多比常规推荐 ±30%，绝不推极端方案
5. 纯 Dart 纯函数，注入 now，可测

【任务 3：推荐引擎 v2 重造】
改造 lib/core/recommendation_engine.dart：
1. 输入升级：当日摄入 + BalanceLedger + 餐次时间 → 输出推荐
2. 模式选择：
   - routine（常规）：当日缺口 + 台账欠账驱动
   - light（清淡）：油脂或谷薯台账盈余 > 0.5 份时激活；
     持续天数由盈余衰减决定（这就是「第二天第三天还推清淡」的来源）
3. light 模式硬规则：
   - 硬排除 fried/high_sodium 标签菜（不是打折，是排除）
   - 主食减量：只推小份话术或 whole_grain 类，份量 ≈ 剩余缺口×限幅
4. 类内质量排序（routine 也生效）：whole_grain > 精白（杂粮饭必须压过白米饭）、
   light > fried
5. 候选过滤：recommendable=false 的菜永远不进推荐（薯条/可乐/奶茶）
   某类候选需该类份数 ≥ 0.5 才算该类候选（防微量蹭位）
6. 推荐份数贴合剩余缺口，不推远超缺口的大菜
7. 修复既有三 Bug：
   - 换一批补位循环：每槽位只取 1 道；菜品标签用菜品自身主导分类，
     不用槽位分类；不再从同一列表连续捞
   - 「已优先清淡」文案：只有实际选出的 3 道全部无 fried/high_sodium 标签才允许出现
   - 水果推荐：换一批后水果槽位不因候选耗尽而静默消失，
     候选不足时显示「水果类候选不足」提示语（引导用户手动记录水果）
8. 保留：多样性惩罚、餐次加成、宠物台词联动

【任务 4：文案与宠物】
1. 超标提醒温和化：「今天主食和油都吃超啦，晚饭清爽一点就好～」
   （不指责，说明影响会持续几天：可以加「这两天咱们吃清淡点」体现滚动调控）
2. 宠物台词按 7 天台账趋势生成：盈余衰减期「昨天吃得很香，今天咱们清爽一点？」
3. 活力值维持现有 3 天口径，确认无「不健康日 → 活力值悬崖式下跌」的惩罚行为

【任务 5：多日仿真测试（核心验收，全部固化）】
新建 test/core/balance_ledger_test.dart 与引擎多日仿真测试：
1. 单日场景：中午炸鸡汉堡薯条可乐（可乐零贡献）→ 晚餐推荐 = 蔬菜类首推 +
   小份 whole_grain 主食，文案提示油/主食超标，无「已优先清淡」以外的欺骗性文案
2. 滚动场景（关键）：
   - Day1 大吃大喝 → Day1 晚 light 模式
   - Day2（无新记录）→ 推荐仍 light（油盈余衰减中），主食仍减量
   - Day3 → 仍略偏清淡
   - Day5~7 → 回归 routine，推荐与常规一致
3. 30 天仿真：随机饮食 + 每餐采用推荐 → 断言 7 天滚动均值收敛进指南目标区间
   （允许 ±20% 容差；这是产品核心指标的自动化证明）
4. 排序断言：杂粮饭 vs 白米饭同时候选时杂粮饭排前
5. 硬断言：任何模式下薯条/可乐/炸鸡不出现（engine 属性测试）
6. 限幅断言：light 模式主食推荐份数下降不超过 30% vs routine
7. 台账单元测试：盈余/欠账衰减曲线、跨周滚动窗口滑动、空数据天处理

【文件权限（另一会话在并行改数据层，严禁越界）】
你只能改：
- assets/data/dietary_guidelines.json、lib/core/models/dietary_guidelines.dart
- lib/core/recommendation_engine.dart、新 lib/core/balance_ledger.dart

严禁碰：assets/data/dishes.json、categories.json、lib/data/food_database.dart、
database_helper.dart、lib/core/models/dish.dart
共享契约：你需要消费菜品模型的 recommendable、quality_tags 字段。

 defensive 解析：JSON 缺字段时用默认值）；
