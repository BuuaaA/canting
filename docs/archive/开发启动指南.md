## 1. 开发前准备

### 1.1 确认环境

在 TraeCode 中打开项目前，确认以下工具可用：

```bash
# 打开终端，依次执行：
flutter --version          # 确认 Flutter 安装
dart --version             # 确认 Dart 安装
flutter doctor             # 检查环境，有问题先修
```

**预期结果**：`flutter doctor` 输出中，Flutter、Android toolchain、Xcode（iOS）至少有一个打勾。

### 1.2 打开项目

1. 打开 TraeCode
2. File → Open Folder
3. 选择 `d:\dev\canting`
4. 等待 Flutter 插件加载完成（右下角会显示 Flutter 版本）

```bash
flutter run
```

或者点 TraeCode 右上角的运行按钮（▶️）。

确认 APP 能正常启动，看到当前 MVP 版本的界面。如果有报错，先修好再继续。

## 2. TraeCode 标准开发流程

> 每个模块都按这个套路来，形成肌肉记忆。

### 2.1 四步开发法

```
读文档 → 出方案 → 写代码 → 验证
  ↓         ↓         ↓        ↓
  3min     2min     10-30min   5-10min
```

#### 第一步：读文档（3 分钟）

- 打开对应模块的 `dev-docs/module-XX-*.md`
- 快速扫：功能描述、涉及文件、数据模型、验收标准
- 同时打开现有的相关代码文件
- 对比：哪些已有？哪些要改？哪些要新建？

#### 第二步：出方案（2 分钟）

在 TraeCode 里给 AI 一个清晰的指令，**让它先出方案，确认后再写代码**。

**标准指令模板**：

```
我要开发【模块名称】。

参考文档：dev-docs/module-XX-xxx.md

现有代码情况：
- 已有文件：lib/xxx/xxx.dart（大概做了什么）
- 需要改造：具体改什么
- 需要新建：哪些文件

请先给我一个改动计划：
1. 哪些文件要改，改什么
2. 哪些文件要新建
3. 整体实现思路
4. 可能的风险点

列清楚，我确认后再开始写代码。
```

**等 AI 输出方案后**：
- 快速过一遍，不合理的地方直接指出来
- 确认 OK 就说「开始实现」

#### 第三步：写代码（10-30 分钟）

**小步快跑原则**：
- 不要让 AI 一次性写 10 个文件
- 按层推进：数据层 → 逻辑层 → UI 层
- 每写完 1-2 个文件就检查一下

**检查要点**：
- 命名对不对？跟项目风格一致吗？
- 逻辑有没有明显问题？
- 跟模块文档对得上吗？
- 有没有引入不必要的依赖？

**发现问题直接说**：
- 「这里命名改一下，跟项目其他地方保持一致」
- 「这个逻辑有问题，应该是...」
- 「少了一个边界情况，...的时候怎么办？」

#### 第四步：验证（5-10 分钟）

1. **跑起来**：`flutter run`，看 APP 能不能正常启动
2. **手动测试**：对照模块文档最后的「验收标准」逐条过
3. **跑单元测试**：`flutter test`，确保已有测试没挂
4. **有 Bug 就修**：把错误信息直接贴给 AI，让它定位修复

### 2.2 一个模块完成后

1. 对照模块文档的验收标准，逐条打勾
2. 提交代码：`git commit -m "feat: 完成模块XX - xxx功能"`
3. 进入下一个模块

## 4. Phase 1：基础骨架

> 目标：数据能落地，设置能走完，APP 重启后数据不丢
> 预计：5 小时

### 模块 1：数据持久化层（3h）

**做什么**：
- 扩展 SQLite 数据库，新增 4 张表：user_profiles / meal_records / pet_states / user_custom_dishes
- 新建 4 个 Repository 类
- 改造 AppState，从数据库加载数据（去掉 Mock）
- 实现数据库版本迁移机制

**开发步骤**：

1. **读文档**：`dev-docs/module-01-persistence.md`
2. **读现有代码**：`lib/data/database_helper.dart`、`lib/state/app_state.dart`
3. **给 AI 指令**：

```
我要开发 V1.0 模块 01：数据持久化层。

参考文档：dev-docs/module-01-persistence.md

现有代码：
- lib/data/database_helper.dart — 目前只有 categories 和 dishes 表，用的 sqflite
- lib/state/app_state.dart — 目前用 Mock 数据
- lib/core/models/ 下已有各种模型类

请帮我：
1. 先分析现有 database_helper.dart 的结构
2. 设计需要新增的表（user_profiles / meal_records / pet_states / user_custom_dishes）
3. 设计数据库迁移机制（版本号管理，onUpgrade）
4. 设计 4 个 Repository 类的接口
5. 给出完整的改动计划

先输出计划，我确认后再写代码。
```

4. **确认方案后**：分步实现
   - 先改 database_helper（加表 + 迁移）
   - 再写 Repository
   - 最后改 AppState
5. **验证**：
   - `flutter run` 看能不能正常启动
   - 走完 onboarding → 杀掉 APP → 重开 → 数据还在吗？
   - `flutter test` 看现有测试过不过

### 模块 2：食物数据库与菜品匹配（2h）

**做什么**：
- 接入膳食指南 JSON 数据
- 完善 DishMatcher，支持用户自定义菜品
- 新增份量估算器（重量 ↔ 份数换算）

**开发步骤**：

1. **读文档**：`dev-docs/module-02-food-db.md`
2. **读现有代码**：`lib/core/dish_matcher.dart`、`assets/data/dietary_guidelines.json`
3. **给 AI 指令**：

```
我要开发 V1.0 模块 02：食物数据库与菜品匹配完善。

参考文档：dev-docs/module-02-food-db.md

现有代码：
- lib/core/dish_matcher.dart — 菜品匹配引擎
- assets/data/dishes.json — L2 菜品数据
- assets/data/dietary_guidelines.json — 膳食指南数据（新增）

需要做：
1. 新建 DietaryGuidelines 数据类，加载 dietary_guidelines.json
2. 完善 DishMatcher，支持从 user_custom_dishes 表中搜索（优先匹配用户自定义）
3. 新建 ServingEstimator：菜名+重量 → 份数，以及反向换算
4. 接入膳食指南的食物交换份数据

先出改动计划，确认后写代码。
```

4. **验证**：
   - 重量输入 → 份数输出是否合理
   - 用户自定义菜品能不能被搜索到
   - 单元测试能不能过

### 模块 3：初始设置流程（2h）

**做什么**：

**开发步骤**：

1. **读文档**：`dev-docs/module-04-onboarding.md`
2. **读现有代码**：`lib/pages/onboarding/`、`lib/core/intake_calculator.dart`
3. **给 AI 指令**：

```

参考文档：dev-docs/module-04-onboarding.md

现有代码：
- lib/pages/onboarding/ — onboarding 页面
- lib/core/intake_calculator.dart — 摄入量计算

需要做：
1. 改造 IntakeCalculator，从 dietary_guidelines.json 取数据而不是硬编码
2. 确认 onboarding 完成后，用户数据写入 user_profiles 表
3. 确认目标份数计算正确并存入用户档案
```

## 9. TraeCode 使用技巧

### 9.1 跟 AI 协作的技巧

| 技巧 | 说明 |
|------|------|
| **先出方案再写代码** | 避免写一半发现设计错了推倒重来 |
| **小步快跑** | 一次让 AI 做一件事，做完检查再继续 |
| **给足上下文** | 把相关的现有代码和文档都告诉它，它写得更准 |
| **贴错误日志** | 跑不通就把报错信息直接贴给 AI，它自己会修 |
| **不确定就问** | "这样设计合理吗？有没有更好的方案？" |
| **指定代码风格** | "跟项目现有代码风格保持一致" |

### 9.2 高效调试

1. **报错先看最后一行**——通常最关键
2. **把完整错误栈贴给 AI**——它能快速定位
3. **加 print 调试**——简单直接，让 AI 加日志
4. **单元测试先行**——核心逻辑先写测试，再写实现

### 9.3 代码质量把控

- 每个模块写完后，快速 Code Review 一遍
- 命名要清晰，不要用缩写
- 复杂逻辑加注释
- 公共方法写 docstring
- 核心逻辑要有单元测试

## 10. 常见问题

### Q1：AI 写的代码跑不起来怎么办？

把错误信息完整复制给 AI，说「这段代码运行报错了，帮我修一下」。通常 2-3 轮就能修好。

### Q2：AI 理解错了需求怎么办？

直接指出来：「不是这个意思，我的需求是...」。最好把模块文档中的相关段落贴给它参考。

### Q3：改动太大，怕改坏了怎么办？

- 小步提交，每个模块一个 commit
- 改之前先 git status 确认改了哪些文件
- 不确定的改动先 stash 或开新分支

### Q4：模块之间有依赖，先做哪个？

按路线图的顺序来就对了。每个 Phase 内部的模块也按编号顺序，编号小的是编号大的依赖。

### Q5：遇到一个问题卡很久怎么办？

1. 先把问题描述清楚，贴给 AI
2. 如果 3 轮还解决不了，换个思路：有没有更简单的实现方式？
3. 实在不行先绕过去，标记为「后续优化」，不要卡在一个点上影响整体进度

### Q6：怎么知道一个模块做完了？

对照模块文档最后的「验收标准」逐条过，全部打勾就算做完了。
